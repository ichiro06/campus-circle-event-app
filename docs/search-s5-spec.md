## 4. 今回の4領域の仕様（DEC-066）

### 4.1 D1 エリア検索

- 初期段階は都道府県・市区町村、後続段階は沿線・駅。元のFR-004にある4項目のうち2項目を先行し、沿線・駅は実装を後続段階へ移す。沿線・駅は削除した要件ではない。
- 同一filter内はOR、異なるfilter間はAND。
- 都道府県と市区町村は、同一の活動場所レコードで一致を確認する。別々の活動場所レコードの値を組み合わせて誤一致させない。
- オンラインのみの活動場所は地理的filterに一致させない。ただし地理的filter未指定時に除外しない。
- 都道府県・市区町村の実装だけで、元のエリア検索Must要件をCOMPLETEにしない。沿線・駅が実装されるまでは元要件に対してPARTIALである。
- 沿線・駅の開発日、リリース日、鉄道マスターの提供元、ライセンス、費用は未決である。推測で設定しない。
- 市区町村の選択粒度（DEC-068 H7）:
  - 初期の選択UI・検索条件では、政令指定都市は市単位とする。行政区単位では検索させない。行政区単位の検索は後続の検討である。
  - 東京都の23特別区は、各区単位で選択・検索できる。
  - 後続で行政区単位を追加できるように、既存の行政区名・元データ・コード情報を失わないデータ設計とする。存在しないコードや由来を推測で補完しない。
  - 上記の同一活動場所での一致、同種OR・異種AND、オンラインのみの場所の扱いは変わらない。

### 4.2 D2 年間費用

- 定義: 団体が自己申告する「入会初年度の標準的な年間費用」。通常の活動参加に必要な費用を対象とし、必須の入会費・会費等を含め、任意イベント等の費用を除く。詳細費用項目からの自動合算は行わない。
- データの意味:

| 状態 | 意味 |
| --- | --- |
| 確定額 | 下限と上限が同額 |
| 金額範囲 | 下限と上限が異なる |
| 未回答 | 金額が分からない状態。0円とは区別する |
| 上限不明 | 下限は分かるが、上限を保証できない状態 |
| 0円 | 実際に費用がかからないことを団体が回答した状態 |

- 検索方式はcontainment。サークルの年間費用範囲全体が、利用者の指定予算範囲内に収まる場合だけ一致する。overlap（範囲が重なれば一致）へ戻さない。

| 予算0〜10,000円 | 結果 |
| --- | --- |
| サークルA（5,000〜8,000円） | 一致 |
| サークルB（5,000〜30,000円） | 不一致 |
| サークルC（上限不明） | 有限予算には不一致 |
| サークルD（未回答） | 0円として扱わない |

- 検索UIは、0円〜20,000円以上を扱う範囲スライダーである。「20,000円以上」の上端は、単なる20,000円の固定上限ではない。
- 上端の意味（DEC-068 H1）: 上端「20,000円以上」の選択は予算上限なしを意味する。20,000円を有限上限として扱わない。サークルが申告した20,000円を超える実額・上限を20,000円へ切り詰めない。予算下限は範囲スライダーの指定値として引き続き有効である。費用filterを指定しない状態と、上限なしを含む範囲を指定した状態は区別する。上端の内部表現・API parameter形式は技術設計 / 実装PRで決める。
- 上限なしの予算と欠損値（DEC-068 H2）:

| 利用者の指定 | 確定額・金額範囲 | 上限不明（下限は既知） | 未回答 |
| --- | --- | --- | --- |
| 有限上限の予算 | containment（DEC-066） | 不一致 | 不一致 |
| 上限なしの予算（上端を選択） | containment（DEC-066）。予算上限は20,000円ではなく上限なしとして扱う（H1） | 既知下限が指定下限以上なら一致 | 不一致 |
| 費用filter無指定 | 除外しない | 費用条件だけでは除外しない | 費用条件だけでは除外しない |

- 未回答（費用の下限・上限とも不明）は、費用filterが有効な場合は一致しない。0円として解釈しない。
- 既存の`circle_costs`費用明細のNULL意味論は変更しない。DBの具体的な符号化・CHECK・migrationは技術設計 / PRレビューの対象である（8節）。

### 4.3 D3 タグ検索

- 初期の通常タグ（初期語彙7種類）: 初心者歓迎、留学生歓迎、兼サーOK、途中入部歓迎、友達作り、少人数、大会あり。複数選択でき、同一filter内はOR、異なるfilter間はAND。
- 選択肢はモバイルにUUIDをハードコードせず、公開タグ一覧APIで提供する。有効なタグを`display_order`順に提示し、非アクティブなタグは表示しない。既存の`tagId` filterを利用する方向である。
- 非アクティブ化の意味（DEC-068 H5、R1）: 非アクティブ化は、新規のタグ選択肢（公開タグ一覧API）から除外することを意味する。次は維持する。
  - 既存の公開revisionに紐付いたタグの表示
  - 既存の`tagId` filterによる検索
  - キーワードによるタグ名検索
- 既存revisionを自動的に書き換えない。不適切なタグを公衆から非表示にするモデレーション操作は、この非アクティブ化とは別仕様であり、今回自動実装しない。
- 初期実装では、運営が指定する人気タグの特別管理、人気タグ専用の検索UI、人気度による特別なランキング、人気判定のための新規集計処理を行わない。これはタグ検索の廃止ではなく、通常タグ検索を初期実装する。
- FR-004の「人気ハッシュタグ」は、初期リリースでは通常タグ検索へ置き換える。人気タグ機能を提供しないまま、元の「人気タグ」要件をCOMPLETEにしない。再導入の時期は未決である。
- 次の2つは別概念であり、混同しない。
  - タグマスター（`tags`）と、Circle側のfeatured tag（`circle_revision_tags.is_featured`。サークルが自分のページで強調するタグ）
  - サービス運営者が全体の人気タグとして指定する機能（初期は提供しない）

### 4.4 D4 活動時間帯

- `TimeBand`の既存値（`morning`、`daytime`、`evening`、`night`、`all_day`、`irregular`）を維持する。`afternoon`等の新しいenum値を追加しない。
- `all_day`の活動枠は、午前・昼・夕方・夜の各時間帯検索に一致する。
- `irregular`は、通常の4つの時間帯検索に一致しない。ただし時間帯filter未指定時に、`irregular`のサークルを検索結果から除外しない。
- 曜日と時間帯が同時に指定された場合は、同一のactivity scheduleレコードで確認する。別々のスケジュールの条件を組み合わせて一致と判定しない。`all_day`と曜日の組合せでも同じである。

| サークルAの活動予定 | 検索条件 | 結果 |
| --- | --- | --- |
| 月曜日・朝（`morning`）、火曜日・夜（`night`） | 月曜日 かつ 夜 | 不一致 |

### 4.5 FR-005 検索結果0件時の導線（DEC-067）

DEC-066 D3と、FR-005の旧完成条件「0件の場合は条件を減らす案内と人気タグへの導線を表示する」の関係を解消する。旧記述は[過去]として履歴に保持する。DEC-066 D3（人気タグの特別扱いは初期除外）は変更しない。

- 0件表示は、通信に成功して該当するサークルがない場合に限る。通信失敗・未取得・権限不足は0件として表示しない。検索条件なし・公開サークル0件の画面は新しく定めず、既存仕様を維持する（D1）。
- 0件画面に「検索条件を見直す」「検索条件をすべて解除」を設ける。「検索条件を見直す」の実装方式は実装PRで決める（D2）。
- 見出し「タグから探し直す」で通常タグ（4.3の7語彙）を提示する。選択前に「選択すると現在の条件を解除し、そのタグだけで検索します」と説明する。選択時はキーワードとすべての絞り込み条件を解除し、選択タグだけで再検索する。並び順は維持する。ほかの絞り込み条件やキーワードが残っている場合、それらとのAND条件によって0件が解消しない可能性があるためである。導線から選べるのは1回の操作につき1つのタグで、追加選択は通常のタグfilterで行う（D3）。
- 「人気タグ」という表現は使わない。人気タグの判定、ランキング、運営指定、専用UI、人気度による特別なランキング、人気判定のための新規集計は行わない（D3）。
- 選択肢は公開タグ一覧API（4.3）で提供し、UUIDをモバイルへハードコードしない。公開タグ一覧APIが利用できない場合や取得に失敗した場合は、タグ導線のみ表示せず、見直し・解除は使える。タグ一覧の取得失敗を検索結果の通信エラー（全画面エラー）として扱わない（D4）。
- 公開タグ一覧APIの未実装期間は、現行の0件画面を暫定的に利用してよい。ただし暫定利用はD2〜D5が実装済みであることを意味せず、タグ導線を実装完了扱いにしない（D4）。
- 実装事実の注記（2026-10-30。上記D4の承認済み条件を変更・延長するものではない。許可条件の期間や解除条件を本書が新たに定めることもしない）:
  - 2026-10-30にPR #46がmainへmergeされ、公開タグ一覧APIのbackend実装は完了した。
  - mobileからのタグ一覧API接続、タグ選択UI、0件時のタグ導線は未実装である。現行mobileには旧0件画面（条件解除のみ）が残っている。
  - DEC-067 D2〜D5は未達で、FR-005はPARTIALである。
  - 「旧画面が現在も存在する」ことは実装事実であり、「暫定利用が現在も許可されている」ことの根拠にはしない。
- タグによる置換後は、直前の検索条件（キーワード、各filter、並び順）へ戻す操作を提供する。アプリ内の一時状態で管理し、サーバー保存や新しい個人情報の収集は行わない。復元可能期間とUIの具体設計は実装時に提案する（D5）。
- 画面上の主要操作（見直し・解除）と補助導線（タグ）の位置付けは`docs/screen-flow.md` 5.2を参照する。

## 7. agentが誤実装しやすいポイント

- 沿線・駅を「削除された要件」と扱う。削除ではなく後続段階である。
- 都道府県と市区町村を、別々の活動場所レコードの値で一致させる。
- オンラインのみの活動場所を、地理的filter指定時に一致させる。または未指定時に除外する。
- 年間費用の検索をoverlapにする。未回答を0円にする。上限不明を有限予算に一致させる。
- 上端「20,000円以上」を有限上限20,000円として扱う。サークルの実額・上限を20,000円で切り捨てる（DEC-068 H1）。
- 上限なしの予算で、上限不明のサークルを一律に除外する。または未回答のサークルを一致させる。費用filter無指定なのに未回答・上限不明を除外する（DEC-068 H2）。
- 費用filter無指定の状態と、上限なしを含む範囲を指定した状態を同一視する（DEC-068 H1）。
- 年間費用のスライダーを、DEC-063の理由で離散chipに変える。
- タグ一覧のUUIDをモバイルにハードコードする。
- 非アクティブ化したタグを、既存の公開revisionの表示、既存`tagId`検索、タグ名のキーワード検索からも消す。既存revisionを自動的に書き換える。非アクティブ化をモデレーション目的の公開抑制として使う（DEC-068 H5）。
- `tags`テーブルに`is_active`列がないと判断して新しい列を追加する（初回migrationで定義済み。ORMに未マッピングだっただけで、2026-10-29の公開タグ一覧API実装PRでマッピングした）。
- タグ検索そのものを削除する。または人気タグ専用UI・ランキング・集計を初期に作る。
- Circle側のfeatured tagと、運営指定の人気タグを同一視する。
- `afternoon`などのenum値を追加する。
- `all_day`を午前・昼・夕方・夜に一致させない。`irregular`を4時間帯に一致させる。時間帯未指定時に`irregular`を除外する。
- 曜日と時間帯を、別々のスケジュール行で評価する。
- 初期段階で政令指定都市の行政区単位の選択・検索を作る。東京都23特別区を都単位にまとめる。行政区名・元データ・コード情報を捨てる、または存在しないコードを推測で補完する（DEC-068 H7）。
- 0件画面の導線に「人気タグ」という表現を使う。または0件時のタグ導線を人気タグ専用UI・人気度による並びとして作る（DEC-066 D3、DEC-067）。
- 0件時にタグを選んでも、キーワードや他のfilterを残したまま検索する（ANDで0件が解消しない可能性がある。DEC-067 D3は条件をすべて解除してそのタグだけで検索する）。置換後に並び順まで初期化する（並び順は維持する）。
- 公開タグ一覧APIの取得失敗を、検索結果の通信エラー（全画面エラー）として扱う。または通信失敗を0件として表示する（DEC-067 D1・D4）。
